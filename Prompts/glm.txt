# STEP 1: PROBLEM UNDERSTANDING

## Problem Restatement

Build **Magnific**, a creative automation pipeline that transforms two character reference images and a creative brief into a set of short animated video clips. The system must:

1. Use Gemini to analyze images and generate structured scene prompts
2. Use an image generation model to produce preview stills maintaining character consistency
3. Use Veo to animate each preview into a cinematic clip
4. Maintain full state through manifest files between stages
5. Support resumability, partial failure handling, and complete external configuration

## Implicit Requirements

| Implicit Need | Why It Matters |
|---------------|----------------|
| Character consistency across outputs | Without it, the output is useless — different-looking characters per scene |
| Veo is async (submit + poll) | Cannot block synchronously; need proper async polling |
| Reference images must be encoded with each API call | Models need to "see" the characters to maintain consistency |
| Job isolation is non-negotiable | Running multiple jobs simultaneously must never corrupt outputs |
| Manifests must be self-contained | Each stage should be runnable with only its input manifest |
| Wall time ≈ slowest video, not sum | User experience demands concurrent video generation |

## Hidden Constraints

1. **Google's API rate limits vary by tier** — we cannot assume unlimited QPS
2. **Safety filters can trigger at any stage** — a "safe" prompt might still get blocked due to image content
3. **Imagen 3 has specific reference image handling** — need to use the correct API surface
4. **Veo operations can get "stuck"** — need timeout handling beyond just retry
5. **Large images may exceed API limits** — need validation/preprocessing

## Assumptions

1. `GOOGLE_API_KEY` has access to: Gemini 1.5 Pro, Imagen 3, Veo 2.0
2. Reference images are JPEG/PNG, under 10MB each
3. Typical job produces 4-12 scenes
4. Video clips are ≤10 seconds each
5. Single-user local execution (no multi-tenant concerns)
6. Local filesystem is reliable and fast

## Success Criteria

- [ ] End-to-end: Two images + text → directory of MP4 files
- [ ] Any single scene failure does not crash the job
- [ ] `--from-stage preview` correctly skips story generation
- [ ] Changing any model/prompt/path requires zero code changes
- [ ] All tests pass without API keys
- [ ] A senior engineer can understand the architecture in <15 minutes

**Input:**
- `story_manifest.json`
- Reference images

**Process:**

   b. Call Imagen with reference images
   c. Download generated image
   d. Update scene status
5. Write `preview_manifest.json`

### Stage 3: Video Animation

**Input:**
- `preview_manifest.json`
- Preview images (only successful ones)

**Process:**
1. Load preview manifest
2. Filter to scenes with status=success
3. Submit all video generation requests (respecting rate limit)
4. Poll all operations concurrently
5. Download completed videos
6. Write `video_manifest.json`

**Output:** `video_manifest.json` + MP4 files

## Manifest Design

**Design Principles:**
1. **Self-contained**: Each manifest has everything needed for its downstream stage
2. **Traceable**: `job_id` links all manifests; `scene_id` links scenes across manifests
3. **Resumable**: Per-scene status allows skipping completed work
4. **Auditable**: Timestamps, error messages, status fields
5. **Validatable**: Strict Pydantic schemas catch corruption

# STEP 3: CONCURRENCY & EXECUTION MODEL

## Concurrency Points

| Location | Concurrency Type | Reason |
|----------|------------------|--------|
| Preview generation | Task-based parallelism | N scenes can generate independently |
| Video submission | Task-based parallelism | Submit requests are independent |
| Video polling | Task-based parallelism | Poll operations are independent |
| Story generation | None | Single LLM call produces all scenes |

## Async vs Sync Decision

**Decision: Full async throughout**

**Reasoning:**
1. Veo polling is fundamentally async (submit → wait → check)
2. Multiple image generations benefit from concurrent I/O
3. Python's `asyncio` provides first-class concurrency without thread complexity
4. Google's Python SDK supports async natively (`google-cloud-aiplatform` with `asyncio`)
5. Single-threaded async avoids GIL contention
6. Simpler mental model: one event loop, no locks needed for API calls

**Trade-off acknowledged:** If we needed CPU-bound work (e.g., image processing), we'd need `run_in_executor`. For this pipeline, all heavy work is I/O-bound API calls.

## Rate Limit Handling

```python
class RateLimiter:
    """Token bucket rate limiter for API calls."""
    
    def __init__(self, calls_per_minute: int):
        self.interval = 60.0 / calls_per_minute
        self._last_call = 0.0
        self._lock = asyncio.Lock()
    
    async def acquire(self):
        async with self._lock:
            now = time.monotonic()
            wait = self._last_call + self.interval - now
            if wait > 0:
                await asyncio.sleep(wait)
            self._last_call = time.monotonic()

class ConcurrencySemaphore:
    """Combines rate limiting with max concurrent requests."""
    
    def __init__(self, max_concurrent: int, rate_limiter: RateLimiter):
        self.semaphore = asyncio.Semaphore(max_concurrent)
        self.rate_limiter = rate_limiter
    
    async def __aenter__(self):
        await self.semaphore.acquire()
        await self.rate_limiter.acquire()
        return self
    
    async def __aexit__(self, *args):
        self.semaphore.release()
```

## Video Polling Strategy

```
Time ──────────────────────────────────────────────────────────────────────▶

Submit V1 ──┐
Submit V2 ──┼──▶ [All submitted] ──▶ Poll V1 ──┐
Submit V3 ──┘                         Poll V2 ──┼──▶ [All done]
                                     Poll V3 ──┘

Wall time = max(poll_v1, poll_v2, poll_v3)
NOT: sum(poll_v1, poll_v2, poll_v3)
```

**Implementation:**
```python
async def generate_all_videos(
    scenes: list[Scene],
    concurrency: ConcurrencySemaphore,
    poll_config: PollConfig,
) -> list[VideoResult]:
    # Phase 1: Submit all (sequentially to respect rate limits)
    operations = []
    for scene in scenes:
        op_id = await submit_video(scene, concurrency)
        operations.append((scene, op_id))
    
    # Phase 2: Poll all concurrently
    tasks = [
        poll_until_complete(scene, op_id, poll_config)
        for scene, op_id in operations
    ]
    return await asyncio.gather(*tasks, return_exceptions=True)
```

# STEP 5: FAILURE HANDLING & RESILIENCE

## Complete Failure Scenario Matrix

| Scenario | Stage | Error Type | Retryable? | Handling |
|----------|-------|------------|------------|----------|
| Rate limit (429/RESOURCE_EXHAUSTED) | Any | Transient | Yes | Backoff + retry |
| Network timeout | Any | Transient | Yes | Backoff + retry |
| Service unavailable (503) | Any | Transient | Yes | Backoff + retry |
| Safety filter (image prompt) | Preview | Permanent | No | Mark scene failed, continue |
| Safety filter (video) | Video | Permanent | No | Mark scene failed, continue |
| Safety filter (story) | Story | Permanent | No | Retry with modified prompt once, then fail |
| Invalid JSON from LLM | Story | Transient | Yes (once) | Retry with stricter prompt |
| Missing required field in JSON | Story | Transient | Yes (once) | Retry with validation hint |
| Image download failed | Preview | Transient | Yes | Retry |
| Corrupt image file | Preview | Permanent | No | Mark scene failed |
| Veo operation failed | Video | Permanent | No | Mark scene failed |
| Veo operation stuck (timeout) | Video | Timeout | No | Mark scene failed |
| Invalid reference image | Any | Input | No | Fail job immediately |
| Reference image too large | Any | Input | No | Fail job immediately |
| Config validation error | Any | Input | No | Fail immediately, show errors |
| Disk full | Any | System | No | Fail immediately |
| Job directory exists | Any | State | No | Load existing job (resume) |

## Retry Strategy

```python
@dataclass
class RetryResult:
    success: bool
    value: Any = None
    error: Optional[Exception] = None
    attempts: int = 0
    total_delay: float = 0.0

async def with_retry(
    fn: Callable[[], Awaitable[T]],
    config: RetryConfig,
    error_classifier: Callable[[Exception], ErrorClass],
) -> T:
    """
    Execute fn with exponential backoff retry.
    
    Error classification:
    - RETRYABLE: Transient errors, will retry
    - PERMANENT: Won't retry, raises immediately
    - RATE_LIMITED: Special handling, longer backoff
    """
    last_error: Optional[Exception] = None
    total_delay = 0.0
    
    for attempt in range(1, config.max_attempts + 1):
        try:
            return await fn()
        except Exception as e:
            error_class = error_classifier(e)
            
            if error_class == ErrorClass.PERMANENT:
                logger.error(f"Permanent error, not retrying: {e}")
                raise
            
            last_error = e
            remaining = config.max_attempts - attempt
            
            if remaining == 0:
                break
            
            # Calculate delay with jitter
            base_delay = config.base_delay_seconds * (config.backoff_multiplier ** (attempt - 1))
            delay = min(base_delay, config.max_delay_seconds)
            
            if config.jitter:
                delay = delay * (0.5 + random.random() * 0.5)
            
            if error_class == ErrorClass.RATE_LIMITED:
                delay *= 2  # Extra backoff for rate limits
                # Respect Retry-After header if present
                retry_after = extract_retry_after(e)
                if retry_after:
                    delay = max(delay, retry_after)
            
            logger.warning(
                f"Attempt {attempt}/{config.max_attempts} failed: {e}. "
                f"Retrying in {delay:.1f}s ({remaining} remaining)"
            )
            await asyncio.sleep(delay)
            total_delay += delay
    
    raise RetryExhaustedError(last_error, config.max_attempts, total_delay)
```

## Idempotency Approach

```python
def should_generate_scene(
    scene: SceneManifest,
    stage_dir: Path,
    output_field: str = "output_path",
) -> bool:
    """
    Determine if a scene needs (re)generation.
    
    A scene is considered complete if:
    1. Status is "success"
    2. Output file exists and is non-empty
    """
    if scene.status != "success":
        return True
    
    output_path = getattr(scene, output_field, None)
    if not output_path:
        return True
    
    full_path = stage_dir / output_path
    if not full_path.exists():
        logger.warning(f"Scene marked success but file missing: {full_path}")
        return True
    
    if full_path.stat().st_size == 0:
        logger.warning(f"Scene file is empty: {full_path}")
        return True
    
    return False
```

## Resume/Restart Logic

```python
class ResumeStrategy:
    """Determines what work needs to be done when resuming."""
    
    def __init__(self, job: Job, from_stage: Optional[str]):
        self.job = job
        self.from_stage = from_stage
    
    def get_execution_plan(self) -> list[tuple[str, bool]]:
        """
        Returns list of (stage_name, should_run) tuples.
        
        Logic:
        - If --from-stage specified: run that stage and all after
        - Otherwise: check each stage's manifest for completion
        """
        stages = ["story", "preview", "video"]
        plan = []
        
        if self.from_stage:
            start_idx = stages.index(self.from_stage)
            for stage in stages[start_idx:]:
                plan.append((stage, True))
        else:
            for stage in stages:
                manifest = self.job.load_manifest(stage)
                if manifest is None:
                    plan.append((stage, True))
                elif manifest.status == "complete":
                    plan.append((stage, False))
                elif manifest.status == "partial":
                    plan.append((stage, True))  # Re-run to fill gaps
                else:
                    plan.append((stage, True))
        
        return plan
```

```python
    async def poll(
        self,

class AudioGenerator(ABC):
```

```python
# src/magnific/providers/__init__.py
from typing import Dict, Type, Any

class ProviderRegistry:
    """Registry for provider implementations."""
    
    _providers: Dict[str, Dict[str, Type]] = {
        "google": {},
        # Future: "openai": {}, "anthropic": {}, etc.
    }
    
    @classmethod
    def register(cls, provider: str, capability: str, impl: Type):
        if provider not in cls._providers:
            cls._providers[provider] = {}
        cls._providers[provider][capability] = impl
    
    @classmethod
    def get(cls, provider: str, capability: str) -> Type:
        try:
            return cls._providers[provider][capability]
        except KeyError:
            raise ValueError(
                f"No {capability} provider registered for '{provider}'. "
                f"Available: {cls._providers}"
            )

def get_provider(provider: str, capability: str) -> Any:
    return ProviderRegistry.get(provider, capability)
```

## Structure Rationale

| Decision | Reasoning |
|----------|-----------|
| `cli/` separate from `core/` | CLI is presentation layer; core should be usable programmatically |
| `config/` as own module | Config is complex (Pydantic models + loading logic), deserves isolation |
| `core/` for shared primitives | Prevents circular imports, makes dependencies explicit |
| `stages/` flat (not nested) | Only 3 stages; nesting adds complexity without benefit |
| `providers/google/` nested | Provider implementations are substantial; may add more providers |
| `tests/` mirrors source | Easy to find test for any module |
| `tests/unit/` vs `tests/stages/` | Unit tests for utilities, stage tests for stage-specific logic |
| `docs/prompts/` external | Prompts are config, not code; easier to iterate |

# STEP 10: SELF-CRITIQUE

## Weak Points Identified

| Weakness | Impact | Mitigation |
|----------|--------|------------|
| Character consistency is best-effort | Output quality may vary | Document limitation; reference images are the best available mechanism |
| No persistent database | Limited querying across jobs | Acceptable for v1; add SQLite in v2 |
| JSON manifests can get large | Disk I/O for many scenes | Unlikely to be problem with <20 scenes |
| No progress UI | Poor UX for long jobs | Could add tqdm in future |
| Single-machine only | Can't scale horizontally | Acceptable for v1; queue system for v2 |

## Over-Engineering Risks

| Potential Over-Engine | Assessment | Decision |
|-----------------------|------------|----------|
| Provider abstraction | Low risk | Small interface, high value if swapping |
| Pydantic config | Low risk | Validation is critical; Pydantic is standard |
| Full async | Medium risk | Adds complexity but necessary for video polling |
| Separate CLI layer | Low risk | Clean separation, easy to test |

## Scalability Limitations

1. **Job count**: Filesystem-based state doesn't scale past ~1000 jobs
2. **Scene count**: No batching for very high scene counts (50+)
3. **Image size**: No preprocessing for very large reference images
4. **Concurrent jobs**: No coordination between parallel job runs

## What I'd Improve With More Time

1. **SQLite job store**: Replace `job_status.json` lookups with proper queries
2. **Progress bars**: Integrate `tqdm` for per-scene progress
3. **Character validation**: Compare generated images to references using embedding similarity
4. **Human-in-the-loop**: Preview review step before video generation
5. **Prompt optimization**: A/B test different prompt strategies for character consistency
6. **Web UI**: FastAPI + HTMX for non-technical users
7. **Cost tracking**: Token/usage logging per job
8. **Image preprocessing**: Auto-resize/compress reference images to optimal size

## Design Decision Revisions

After self-critique, I'm adjusting:

1. **Originally**: Considered SQLite from start
   **Revised**: Start with JSON manifests, add SQLite as optional backend later. YAGNI for v1.

2. **Originally**: Complex scene dependency graph
   **Revised**: Linear scene order is sufficient. Dependencies add complexity without clear value.

3. **Originally**: Separate config for each stage
   **Revised**: Single config file with namespaced sections. Simpler to manage.

# Summary of Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Language | Python 3.11+ | Google SDK, async support, type hints |
| Async model | Full asyncio | Video polling demands async; consistent model |
| Config format | YAML | Human-readable, comments, standard |
| Config validation | Pydantic v2 | Industry standard, performant |
| Manifest format | JSON | Universal tooling, no comments needed |
| State storage | Filesystem | Simple, debuggable, no DB dependency |
| Job ID | UUID v4 | Unique, no coordination needed |
| CLI framework | Click | Mature, type hints, good docs |
| Testing | pytest + mocks | Standard, clear, no real API calls |
| Retry | Exponential backoff + jitter | Industry standard, avoids thundering herd |
| Rate limiting | Token bucket | Smooth request distribution |
| Provider abstraction | ABC classes | Simple, explicit, testable |
