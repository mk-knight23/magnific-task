STEP 1: PROBLEM UNDERSTANDING
Restatement
Magnific is a 3-stage creative pipeline that transforms character references + a creative brief into animated video clips. The core challenge isn't just calling APIs—it's building a resilient, observable, resumable production system where:
Each stage produces inspectable artifacts (manifests)
Failures are contained and recoverable
The system is configurable without code changes
Multiple scenes are processed concurrently within API constraints
Implicit Requirements
Idempotency: Re-running a stage with the same inputs should be safe
Observability: We need to know what succeeded/failed without reading logs
Resource management: API quotas, disk space, concurrent connections
Character consistency: Stage 2 must maintain character identity across scenes
Polling efficiency: Video generation is async; we must poll smartly
Assumptions
A1: Google API provides standard HTTP status codes for rate limits (429) and safety blocks (400/403)
A2: Image generation model accepts text prompts + reference image conditioning (implied by "consistent character designs")
A3: Reference images are reasonable size (<10MB) and valid formats
A4: Evaluator runs on a machine with Python 3.11+, internet access, and local filesystem
A5: "Concurrent video-generation polling" means we poll multiple video jobs simultaneously, not that video generation itself is parallelized per scene
Success Criteria
End-to-end pipeline runs with single command
Each stage can run independently
Failed scenes don't crash the pipeline
Config changes don't require code changes
Tests pass without real API keys

STEP 3: CONCURRENCY & EXECUTION MODEL
Where Concurrency Is Used
Table
Location	Model	Rationale
Stage 2 (Preview)	ThreadPool	Image generation is I/O-bound (HTTP API calls). Threads are sufficient; async adds complexity without benefit since we're using blocking SDKs
Stage 3 (Video)	Asyncio + ThreadPool	Video generation requires polling. We submit all videos, then poll all concurrently. Asyncio for polling loops, threads for blocking API calls
Why Not Full Async?
Decision: Hybrid model (sync for simple calls, async for polling).
Rationale:
Google GenAI SDK is primarily synchronous
Converting everything to async adds complexity for marginal gain
ThreadPoolExecutor handles concurrent I/O-bound image generation well
Asyncio shines for managing hundreds of polling coroutines with asyncio.gather
Rate Limiting Strategy
Python
Copy
# Token bucket per provider
class RateLimiter:
    def __init__(self, requests_per_minute: int):
        self.tokens = requests_per_minute
        self.last_refill = time.monotonic()
        self.lock = threading.Lock()
    
    def acquire(self):
        with self.lock:
            self._refill()
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False
One limiter per API provider (Gemini, Image, Veo)
Configurable RPM from config file
Blocking wait with timeout rather than immediate failure

│  │ backoff │ │ backoff │ │ backoff │  │
│  │ 5s→10s  │ │ 5s→10s  │ │ 5s→10s  │  │
│  └────┬────┘ └────┬────┘ └────┬────┘  │
│       └─────────────┴───────────┘       │

└─────────────────────────────────────────┘
Key insight: Video generation wall time ≈ slowest video, not sum. We poll all concurrently with exponential backoff (5s, 10s, 20s, 30s cap).

STEP 5: FAILURE HANDLING & RESILIENCE
Failure Scenarios & Responses
Table
Scenario	Detection	Response	Manifest Update
Rate limit (429)	HTTP status	Exponential backoff, retry	status: "retrying"
Timeout	requests.Timeout	Retry with backoff	status: "retrying"
Safety filter	API error / empty output	Skip scene if configured, or fail	status: "blocked", error: "safety"
Invalid JSON	json.JSONDecodeError	Retry with stricter prompt, then skip	status: "failed"
Schema validation fail	Pydantic ValidationError	Log details, skip scene	status: "failed"
Corrupt image	PIL UnidentifiedImageError	Skip scene	status: "failed"
Disk full	OSError (ENOSPC)	Immediate fail, preserve state	Pipeline halt
API key invalid	401/403	Fail fast, no retry	Pipeline halt
Retry Strategy
Python
Copy
@dataclass
class RetryPolicy:
    max_retries: int = 5
    base_delay: float = 1.0
    max_delay: float = 60.0
    exponential_base: float = 2.0
    retryable_statuses: set[int] = field(default_factory=lambda: {429, 500, 502, 503, 504})
    
    def calculate_delay(self, attempt: int) -> float:
        delay = self.base_delay * (self.exponential_base ** attempt)
        return min(delay, self.max_delay) + random.uniform(0, 1)  # Jitter
Idempotency
Stage 1: Deterministic given same seed (if supported) or re-runnable
Stage 2: Overwrites existing previews if re-run (idempotent)
Stage 3: Re-submits videos if re-run (Veo generates new videos each time—acceptable)
Resume Logic

def determine_resume_point(job_dir: Path) -> Optional[str]:
    """Check manifests to find where to resume."""
    if not (job_dir / "manifest_03_video.json").exists():
        if (job_dir / "manifest_02_preview.json").exists():
            return "video"
        if (job_dir / "manifest_01_story.json").exists():
            return "preview"
    return None

Validates that previous stage manifest exists
Loads parent manifest as input

Reads job directory manifests
Reports: job_id, current stage, scenes completed/total, any failures
Exit 0 if complete, 1 if failed, 2 if running (for scripting)

STEP 10: SELF-CRITIQUE
Weak Points
No persistent queue: If the process crashes mid-poll, video operation IDs are lost. Mitigation: save operation IDs to manifest immediately after submission.
File-based state: Doesn't scale to distributed execution. For single-machine evaluation, this is correct; for production, we'd add Redis/PostgreSQL.
No content addressing: Re-running with same inputs regenerates everything. Could add content-hash caching.
Polling inefficiency: Fixed intervals rather than webhook/callback. Veo doesn't support webhooks, so this is unavoidable.
Over-Engineering Risks
Avoided: Full async/await throughout (unnecessary complexity)
Avoided: Microservices (single Python package is correct for this scale)
Avoided: Database layer (filesystem is sufficient)
Scalability Limitations
Max concurrent scenes limited by preview.max_concurrent (configurable)
Disk usage grows linearly with scenes × stages
No garbage collection of old jobs
What I'd Improve With More Time
Add SQLite state store for operation ID persistence and job querying
Implement content-addressable cache to skip re-generation of identical previews
Add structured logging (JSON) with correlation IDs for observability
Add progress bars (tqdm/rich) for CLI UX
Add pre-flight checks (API key validation, disk space, model availability)
